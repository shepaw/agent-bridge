# M2 立项：taskReplay 跨重启持久化

状态：待评审 · 提出：2026-09-21 · 归属：shepaw-acp-sdk（对话链路）

## 1. 问题

`ACPAgentServer` 的断线续传依赖一个**纯内存**的重放缓冲 `taskReplay`（`sdks/shepaw-acp-sdk-typescript/src/server.ts`）：

- 每个 chat task 一个条目，存累计文本、末次 metadata、未决确认卡片、终态结果。
- 客户端断线后 turn 继续跑（detached），重连用 `agent.taskResume` + `known_length` 取回缺失后缀。
- 但缓冲**不落盘**：TTL 25 分钟、单任务文本上限 4M code units，超限时 `status: 'lost'`。

由此产生的失败：

1. **SDK 进程重启（升级/崩溃/宿主重启）**：所有在飞 turn 的重放状态全丢，重连一律返回 `lost`。用户侧表现为"回复到一半，回来变成任务丢失"。
2. **超过 4M 上限的长 turn**：同样判 `lost`，尽管 turn 其实还在跑。
3. **未决确认卡片丢失**：这是最痛的——权限卡已经发出、用户还没点，进程一重启卡片消失，turn 永久停在等待审批（与已修的 S2 叠加时会挂死）。

## 2. 目标 / 非目标

目标：
- 进程重启后，未决确认卡片与终态结果**必须**可恢复。
- 在飞文本**尽力**恢复：不追求 4M 全量，恢复最近的一段即可（用户看到"继续输出"比"丢失"好得多）。
- 协议与客户端行为不变：`agent.taskResume` 的语义、字段不变。

非目标：
- 不做跨设备/跨节点同步（那是 Hub 层的职责）。
- 不做历史会话归档（已有 session-history / transcript sink 负责）。

## 3. 方案（推荐：受限镜像）

只落盘"恢复所必需"的三块，避免把全部对话文本写盘：

| 数据 | 是否落盘 | 说明 |
|---|---|---|
| `pendingConfirmations` | ✅ 全量 | 卡片体积小，且是审批能否继续的关键 |
| 终态 `status` / `result` / 时间戳 | ✅ | 让重启后重连直接拿到 done/error |
| 累计文本 | ⚠️ 截断保留尾部（建议 64 KB） | 足够接上"继续输出"，不必承担 4M 的写盘成本与隐私面 |
| 末次 metadata | ✅ | 体积极小 |

要点：
- 写入用**防抖**（建议 500ms）+ 终态立即 flush，避免每个 chunk 都写盘。
- 启动加载时按 TTL 清理过期条目；超过截断上限的旧文本不再增长（仍记为 overflow，但不再判 `lost`，而是降级为"从尾部恢复"）。
- 存储位置由实现方注入（新增可选项，如 `ACPAgentServer` 构造参数的 replay 目录），**默认关闭**——SDK 作为库不应擅自决定写哪里；由 acp-proxy / hub 打开并指定目录。
- 磁盘格式：单文件 JSON 或每任务一文件两种皆可，必须原子写（tmp + rename，避免崩溃留下半截文件）。

## 4. 备选方案

- **B 仅持久化卡片**（最轻）：只解决"审批丢卡"，文本仍然丢失。工作量约为 A 的 1/3，可作为第一阶段。
- **C 维持现状**：接受丢失，仅把 TTL/上限调大。不推荐——重启场景无解。

建议先做 B（一个迭代内可完成并验证），再按反馈扩展到 A。

## 5. 验收标准

1. 进程重启后，未决确认卡片能通过 `agent.taskResume` 重新推送（有测试）。
2. 重启后终态 task 仍能返回 `done` + 终态结果，而非 `lost`。
3. 超过文本上限时，行为是"尾部降级恢复"而非直接 `lost`；不崩溃、不写坏文件。
4. TTL 过期条目被清理，磁盘不无限增长。
5. 关闭持久化（默认）时行为与今天完全一致——既有 293 + 363 用例不回归。

## 6. 风险

- **隐私**：对话文本落盘。需与现有 resume / transcript 落盘策略一致（同目录、同权限），并在文档中明示。
- **写盘频率**：必须防抖，否则长 turn 会持续 I/O。
- **并发**：SDK 多实例共用目录时要按 device/agent 隔离文件名。
